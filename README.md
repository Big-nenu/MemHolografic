# MemHolografic 🧠✨

**Concepto:** Arquitectura de Memoria Híbrida para Agentes de IA.

## 🌌 La Visión
Pasar de un asistente tipo "Jarvis" (precisión en hechos) a una entidad tipo "Vision" (aprendizaje evolutivo y autónomo). El objetivo es combinar la estabilidad de los hechos inmutables con la capacidad de auto-mejora continua.

## 🌊 Principios de Diseño (Analogía de Ondas)

### 1. Interferencia Constructiva (Guardado)
En lugar de almacenar datos redundantes, el sistema utiliza la analogía de la mecánica cuántica:
- Cuando dos memorias contienen la misma información, chocan y se **unifican**.
- Las redundancias se cancelan y las verdades se refuerzan, creando una "Onda Maestra" de conocimiento.
- **Resultado:** Memoria optimizada, sin basura y con datos validados.

### 2. Recuperación Asociativa en Cascada (Consulta)
La búsqueda no es lineal, sino expansiva:
- Una consulta dispara una "onda" que trae el dato principal y automáticamente activa nodos relacionados.
- **Flujo:** `Dato A` $\rightarrow$ `Datos Relacionados B, C, D` $\rightarrow$ `Síntesis de Respuesta`.
- **Resultado:** Respuestas con contexto total, reduciendo la necesidad de múltiples preguntas.

## 📂 Gestión de Olvido: El Sótano de Memoria (The Basement)
Basado en la premisa de que el cerebro no olvida, sino que oculta la información, se implementó un sistema de **Memoria de Archivo**:
- **Mesa de Trabajo (`facts`):** Almacena recuerdos activos con energía alta.
- **El Sótano (`archived_facts`):** Cuando un dato pierde energía (por falta de uso o contradicciones), no se borra, sino que se mueve al Sótano.
- **El Bibliotecario (Resurrección):** El proceso de consulta busca primero en la mesa de trabajo. Si no encuentra respuesta, el Bibliotecario "baja al sótano", recupera el dato y lo **resucita** devolviéndolo a la memoria activa con energía renovada.

## 🔮 Camino hacia el Cerebro Digital
Para pasar de un "motor de memoria" a un **"Cerebro Digital"**, se han trazado tres caminos evolutivos:

### 1. El Sótano de Memoria (Decaimiento y Resurrección) 📉
Inspirado en la idea de que el cerebro no borra, sino que oculta.
- **La Idea:** La energía de una onda disminuye con el tiempo. Si un dato no se consulta, cae al Sótano (`archived_facts`). Si se vuelve a buscar, el Bibliotecario lo resucita.
- **El Efecto:** Mantiene la memoria limpia de ruido sin perder información valiosa.
- **Estado:** IMPLEMENTADO Y VALIDADO.

### 2. El "Puente Semántico" (Asociaciones Cruzadas) 🌉
La verdadera inteligencia ocurre cuando conectas dos cosas que no se parecen, pero tienen una relación.
- **La Idea:** Crear una función de "Búsqueda de Puentes" que busque una onda intermedia entre dos temas totalmente distintos (ej. "Café" y "Física Cuántica").
- **El Efecto:** Permite al sistema generar conexiones inesperadas, siendo el paso previo a la **creatividad artificial**.

### 3. "La Reflexión Autónoma" (Active Dreaming) 🌙✨
Convertir el proceso de sueño de una limpieza técnica a un proceso creativo.
- **La Idea:** Que durante el `dream()`, la IA analice ondas de alta energía y genere hipótesis propias: "Tengo datos de X y Y... ¿podría ser que X sea la causa de Y?".
- **El Efecto:** El sistema empezaría a crear intuiciones autónomas que luego intentará validar en la conversación.

## 🛠️ Resolución de Problemas (Troubleshooting Guide)

Durante la fase de integración con Cline (vía MCP), se identificaron y documentaron los siguientes errores críticos, junto con sus soluciones aplicadas.

### 1. Error de Conexión MCP: "Connection closed" 💀
- **Síntoma:** El servidor MCP (`memholografic`) aparecía en rojo en Cline, indicando que no podía conectarse.
- **Diagnóstico:** Al ejecutar el servidor `mcp_server.py` manualmente desde la terminal, se reveló un `SyntaxError` oculto dentro de `mem_engine.py`. La causa raíz fue una corrupción del código: caracteres extraños (`//`) se habían insertado accidentalmente en varios nombres de variables y tablas (ejemplos: `archived_//facts`, `self.db_//path`, `max_//sim`). Esto provocó que el intérprete de Python cerrara el proceso antes de iniciar correctamente el handshake con Cline.
- **Solución:** Se realizó una limpieza exhaustiva del archivo `mem_engine.py`, eliminando todos los artefactos y asegurando una sintaxis válida. Se verificó que el servidor arrancara sin errores ejecutándolo directamente.
- **Lección:** Los errores de conexión en servidores MCP a menudo oculta un fallo de arranque del proceso. Siempre verifique el *log de error* ejecutando el script manualmente.

### 2. Error de Ruta de Python: "spawn ENOENT" 🤖
- **Síntoma:** Cline no podía encontrar el intérprete de Python especificado en `cline_mcp_settings.json`, lanzando un error `ENOENT`.
- **Diagnóstico:** La ruta `C:\Users\Luis_Hdez\AppData\Local\Programs\Python\Python314\python.exe` especificada en la configuración no existía en el sistema. El comando `where python` reveló las rutas válidas.
- **Solución:** Se corrigió la ruta del ejecutable de Python en `cline_mcp_settings.json` al valor verificado: `C:\Program Files\Python314\python.exe`.
- **Recomendación General:** Siempre utilice el comando `where python` para obtener la ruta absoluta del intérprete antes de configurar un servidor MCP.

### 3. El Concepto de Namespace y Aislamiento de Memoria 🧠
- **Qué es un Namespace en MemHolografic?** Es un "proyecto ID" o "etiqueta de contexto". Los recuerdos inyectados se guardan bajo un namespace. Cuando la IA consulta, solo busca dentro del namespace activo. Esto evita que la memoria de un proyecto se mezcle con la de otro.
- **Namespace por defecto:** El servidor MCP usa `"default"` como namespace si no se especifica otro.
- **Namespace Personalizado:** Puedes usar un namespace específico (ej: `"neodata"`, `"investigacion"`, `"personal"`) para separar la memoria por contexto. Esto es útil si quieres mantener memoria de trabajo independiente de tu memoria personal.

## 🏗️ Arquitectura Profesional (28 de Octubre 2026)

Para garantizar que el software sea distributable, escalable y seguro, se realizó una reestructuración profunda del código:

### 1. Persistencia en Home Directory (`.memholografic`) 🏠
- **Antes:** Las bases de datos se guardaban en la carpeta del repositorio (`data/memoria-2.db`). Esto implicaba que al borrar el proyecto, se perdía toda la memoria.
- **Ahora:** El sistema utiliza `Path.home()` para crear una carpeta oculta `.memholografic` en el perfil del usuario.
- **Beneficio:** La memoria es persistente a nivel de sistema operativo. Si el usuario clona el repositorio en otra carpeta o lo borra, sus recuerdos permanecen intactos en su perfil.
- **Ruta por defecto:** `~/.memholografic/memoria.db`

### 2. Identidad Dinámica (Eliminación de Hardcoding) 👤
- **Antes:** `mem_engine.py` contenía una lista manual `ENTITY_ALIASES` con el nombre del desarrollador para unificar entidades en el grafo. Esto era un error de diseño que impedía el uso en otros usuarios.
- **Ahora:** Se implementó `os.getlogin()` para detectar dinámicamente al usuario del sistema. El sistema normaliza automáticamente cualquier mención al usuario actual (ej. "Luis", "Usuario") hacia su identidad real sin necesidad de edición manual.

### 3. Modularización: Separación de Responsabilidades 🏗️
- **`mem_engine.py`:** Ahora es un núcleo limpio enfocado exclusivamente en la lógica de memoria (inyección, consulta, sueño, reflexión).
- **`graph_engine.py` (Nuevo):** Se creó este módulo exclusivo para la extracción de entidades y la generación de grafos HTML. Esto permite que el motor de memoria sea ligero y que la visualización se pueda evolucionar de forma independiente.

### 4. Migración Automática
- Se implementó lógica para detectar y migrar bases de datos antiguas a la nueva ubicación profesional si es necesario.

## 🚀 Roadmap: Búsqueda por Temas (memoria rápida y escalable)

**Objetivo:** Que la consulta no tenga que comparar contra *todas* las filas de la BD, sino solo contra los temas relevantes.

### Problema actual
Hoy `query_memory` convierte la pregunta en un vector con `embeddinggemma`, lo compara contra **todos** los vectores guardados en `facts`, y devuelve los más similares. Funciona bien con cientos de recuerdos, pero se vuelve lento con miles.

### Propuesta de arquitectura

```
Tabla facts (actual):
  id, namespace, content, energy, embedding

Nueva tabla topics:
  id, topic_name, description

Nueva tabla fact_topics (relación muchos-a-muchos):
  fact_id, topic_id
```

### Flujo de consulta con temas

1. **Al inyectar (`inject_memory`):** El modelo `tev` clasifica el contenido en uno o más temas (ej. "física", "videojuegos", "proyecto"). Se guarda la relación en `fact_topics`.
2. **Al consultar (`query_memory`):**
   - Paso A: `tev` detecta los temas de la pregunta (ej. "¿Qué estudiaste?" → tema "educación", "carrera").
   - Paso B: Se filtran solo los `facts` vinculados a esos temas.
   - Paso C: Se calcula similitud cosínea solo dentro de ese subconjunto (mucho más rápido).
3. **Resultado:** Menos comparaciones, respuestas más rápidas, y escalable a miles de recuerdos.

### Índices de SQLite
Para acelerar aún más sin dependencias externas, se agregarían índices:
```sql
CREATE INDEX idx_facts_namespace ON facts(namespace);
CREATE INDEX idx_fact_topics_topic ON fact_topics(topic_id);
CREATE INDEX idx_fact_topics_fact ON fact_topics(fact_id);
```

### Opción opcional para escala masiva
Si el proyecto crece mucho, se puede migrar el índice vectorial a una librería ligera como `faiss-cpu` o `chromadb`, manteniendo SQLite solo para metadatos. Esto se dejaría como módulo opcional para no complicar la instalación básica.
